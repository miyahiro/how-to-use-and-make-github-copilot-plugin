# 内部設計テンプレートと記載ガイド

## 適用方法

内部設計は、要件と外部設計をどの構造・処理で実装・運用・検証するかを定義する。機能ごとに、コンポーネント・クラス等の責務、配置層、契約、連携を具体化する。

- 設計文書は要件定義の機能文書と同じ単位とし、`docs/spec/current/design/<機能>.md`（`requirements/<機能>.md` と同じファイル名）に1つ作る。内部設計はその文書の「内部設計」の部に、外部設計の部の後に書く。
- 文書がなければ（外部設計が不要な場合など）、下記の「文書の冒頭」と「内部設計」の部を作り、冒頭の「外部設計」の行に省略の理由を書く。
- 全体共通のアーキテクチャ、層の責務・依存規則、セキュリティ・運用方針は共通設計（`design/README.md`）に置き、機能文書から参照する。機能固有の設計と共通方針への例外を記載する。
- 既存文書には内容を既存の章立て・表形式へ対応付けて記述する。既存文書自体を標準書式へ一律変換せず、機能境界・ID・意味・参照関係を保持する。対応先のない必要項目だけ最小限の節を追加する。
- 規模や複雑さに応じて詳細を分けてよいが、目次の数だけファイルを作らず、1クラス1文書も強制しない。構成・依存・処理・データを横断して追える参照を残す。
- クラスのない実装では、モジュール・関数・型で同じ責務と契約を記述する。全クラスの細かな補助メソッドやコード本体を固定する必要はないが、コンポーネント間の契約と責務分担を曖昧にしない。
- 全章の記入を目的にしない。単純な処理に不要なDDDモデル・層・抽象化を増やさない。DBや非同期処理がない場合などは該当しない理由を示す。ただし実装に必要な判断の不足を任意項目として省略せず、未確認と該当なしを区別する。

## 要件定義・外部設計との対応

| 入力 | 内部設計での使い方 |
| --- | --- |
| 要件の対象範囲 | 1. の対象内外、10. の変更影響 |
| 要件の機能要件 | 2. の構成、5. のユースケース |
| 要件の業務ルール | 3. の不変条件・ルール（根拠の要件 ID を書く） |
| 要件の非機能要件 | 8. の機能固有の実現方法 |
| 要件の受入条件 | 9. の検証方法と環境 |
| 要件の未解決質問 | 期限が設計のものを 10. の未解決質問へ引き継ぐ。回答のないまま確定しない |
| 外部設計の部 | 1.・5.・7. で参照し、外部から見える動き・契約を変えずに実現方法を書く |

## 目次と記載内容

| 標準目次 | 記載する内容 |
| --- | --- |
| 1. 設計対象・概要 | 関連要件・外部設計・受入条件、対象ユースケース、対象内外、共通設計・技術制約。 |
| 2. 機能構成・層配置 | コンポーネント一覧・構成図、配置層、依存方向、他機能との境界、依存を組み立てる場所。 |
| 3. ドメイン設計 | 用語・業務ルール・不変条件、必要なコンテキスト・集約・エンティティ・値オブジェクト・ドメインサービス。 |
| 4. コンポーネント・クラス設計 | 各クラス・モジュールの責務、公開インターフェース、保持する状態、不変条件、依存先、実装配置、検証観点。 |
| 5. 処理設計 | ユースケースの入出力・事前事後条件、呼び出し順・分岐、認可、トランザクション、例外処理。 |
| 6. データ・永続化設計 | スキーマ、モデルとの対応、制約・索引、取得・更新、整合性・競合制御、保持・削除。 |
| 7. 内部通信・外部接続の実装設計 | 内部API・イベント・連携アダプター、外部契約との対応、タイムアウト・再試行・冪等性・順序・障害回復。 |
| 8. 非機能・運用設計 | 性能・セキュリティ・ログ・監査・監視・設定、共通処理の適用、配置・起動など機能固有の運用。 |
| 9. テスト設計 | 要件・受入条件との対応、単体・結合・契約・E2E・非機能テスト、データ、モック境界、実行環境。 |
| 10. 変更影響・技術判断 | 互換性、既存モデル・呼び出し元への影響、移行・切り戻し、技術・ライブラリの採用理由・代替案、質問。 |

## 記載・確認ルール

- 共通設計があれば、そのアーキテクチャに従って配置層を示す。未定義なら内部設計で共通構成を設計して `design/README.md` に置き、機能別の設計と合わせて設計の承認でまとめて確かめる。アーキテクチャだけの承認は設けない。プレゼンテーション、コントローラー、アプリケーション、ドメイン、インフラストラクチャなどの構成を使う場合も、すべての機能に全層を作るとは限らない。
- コンポーネントの静的な依存方向と実行時の呼び出しを区別する。ポートの定義先と実装先を示し、業務判断をインフラへ埋め込まない。既存構成に例外が必要なら根拠・代替・影響を承認者へ確認する。
- 新規設計には `DES-<機能>-001` 形式（`<機能>` は要件 ID と同じ英大文字の略号）の安定IDと対応する要件 ID を付け、既存IDを保持する。設計IDは外部・内部設計を通じて共通の名前空間とし、同じ文書の既存の設計IDを確認して未使用の3桁番号を選ぶ。異なる設計項目に同じIDを割り当てず、同じ項目の参照・再掲には同じIDを使う。ドメインの不変条件、クラスの契約、処理順、データ制約が矛盾しないことを確認する。
- 外部設計の動作・契約は参照し、ここでは実現方法を記載する。要件や外部設計の変更が必要になったら、内部実装で辻褄を合わせず要件定義または外部設計へ戻す提案をする。
- 必須の技術判断を推測で確定しない。質問には選択肢・推奨と根拠・影響・確認期限の工程を添え、該当する設計を止めて窓口へ返す。
- 各受入条件に検証方法と環境を対応付ける。タスク一覧（`tasks.md`）の確認方法はこれをもとにする。検証の計画と実施済みの証跡を区別し、環境が利用できない場合の手動確認と未実施の扱いを示す。
- 設定・秘密情報は参照名と管理方法のみを記載し、秘密値を含めない。工程の承認と案件の状態は `status.md` と承認のコミットで扱う。コードをこの設計作業で編集しない。

## 新規文書のテンプレート

プレースホルダーを確認済みの内容へ置き換える。コンポーネントやユースケースの詳細は対象ごとに繰り返す。該当しない節は理由を示して統合・省略できる。

### 文書の冒頭（設計文書がないときだけ作る）

```markdown
# <機能名>の設計

入力: [<機能名>の要件](../requirements/<機能>.md)
共通設計: [README.md](README.md)
外部設計: <この文書の「外部設計」の部。不要なら理由を1行>
```
