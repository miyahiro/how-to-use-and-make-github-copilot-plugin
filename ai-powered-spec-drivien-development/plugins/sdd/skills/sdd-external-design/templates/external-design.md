# 外部設計テンプレートと記載ガイド

## 適用方法

外部設計は、UI・帳票・公開 API・CLI・外部連携について、利用者や外部システムに見える動きと契約を定義する。内部クラス、DBの物理構造、処理の実装方式は内部設計に置く。

- 設計文書は要件定義の機能文書と同じ単位とし、`docs/spec/current/design/<機能>.md`（`requirements/<機能>.md` と同じファイル名）に1つ作る。外部設計はその文書の「外部設計」の部に、内部設計は同じ文書の「内部設計」の部に書く。
- 文書がなければ、下記の「文書の冒頭」と「外部設計」の部を作る。内部設計が先に文書を作っていれば、「外部設計」の部だけを内部設計の前に足す。
- 利用者や外部システムに見える動きが変わらない機能では部を作らず、文書の冒頭の「外部設計」の行に理由を1行書く。省略に別の承認は置かず、設計の承認でまとめて確かめる。
- 対象となる種類だけを記載する。UI・帳票・外部連携のすべてを必須にしない。CLI・対話型ツールでは、UI設計をコマンド・対話の入出力と状態の設計に置き換える。
- 既存文書には内容を既存の章立て・表形式へ対応付けて記述する。既存文書自体を標準書式へ一律変換せず、機能境界・ID・意味・参照関係を保持する。対応先のない必要項目だけ最小限の節を追加する。
- 全体共通の表示・権限・エラーなどは共通設計（`design/README.md`）を参照し、固有の内容を各機能に記載する。画面・帳票・連携単位で詳細を繰り返す。
- 同一システム内のUIとバックエンドの通信を、すべて外部連携と扱わない。利用者に見える動作と公開APIの契約は外部設計、内部APIの技術的な契約は内部設計に置く。
- 全章の記入を目的にしないが、対象となる外部動作・契約の不足を任意項目として省略しない。該当なしと未確認を区別し、対象外は理由を示す。

## 要件定義との対応

| 要件定義の節 | 外部設計での使い方 |
| --- | --- |
| 利用者と利用場面 | 1. の利用者・シナリオ、画面遷移や操作の流れ |
| 対象範囲 | 1. の対象内外、外部システムとの境界 |
| 機能要件 | 画面・帳票・連携の一覧と、操作・出力・連携の正常・例外時の動き |
| 業務ルール | 入力チェック、権限、表示・算出の条件。ルールは要件文書を参照し、書き写して変えない |
| 非機能要件 | 処理中の表示、アクセシビリティ、タイムアウト・再試行など外から見える品質 |
| 受入条件 | 5. の外部動作の確認観点 |
| 未解決質問 | 期限が設計のものを 5. の未解決質問へ引き継ぐ。回答のないまま確定しない |

## 目次と記載内容

| 標準目次 | 記載する内容 |
| --- | --- |
| 1. 設計対象・概要 | 対象機能、関連要件・受入条件、利用者・シナリオ、対象内外、共通設計への参照。 |
| 2. UI設計 | 画面一覧・遷移、各画面のレイアウト・項目・操作・状態・入力チェック・権限・エラー表示。レスポンシブ・アクセシビリティ上の振る舞いも扱う。 |
| 3. 帳票設計 | 帳票一覧、各帳票のレイアウト、項目の意味・算出方法、抽出条件・集計・並び順、出力形式・操作・権限、異常時動作。 |
| 4. 外部連携設計 | 連携一覧、各連携の相手・目的・方向・タイミング、項目・形式・認証などの契約、正常・異常動作、互換性。 |
| 5. 要件対応・確認事項 | 要件・受入条件と設計箇所の対応、受入確認の観点、判断根拠・出所、未解決質問、対象外理由。 |

## 記載・確認ルール

- 画面項目・帳票項目・連携データは、物理的な保存構造ではなく外部から見える意味を定義する。既存の業務ルールは参照し、表示や帳票の計算式がそれと矛盾しないようにする。
- 操作・出力・連携には事前条件、正常結果、権限、必要な例外時の結果を示す。再試行や中断を許す場合は、重複や処理済み状態が外部からどう見えるかを定義する。
- 要件・非機能要件・受入条件との対応を維持する。新規設計には `DES-<機能>-001` 形式（`<機能>` は要件 ID と同じ英大文字の略号）の安定IDを付け、画面・帳票・連携の識別子と一覧表で対応付ける。これらの識別子は既存規則があれば従い、なければ機能内で一意な識別子とする。
- 設計IDは外部・内部設計を通じて共通の名前空間とする。同じ文書の既存の設計IDを確認し、未使用の3桁番号を選ぶ。異なる設計項目に同じIDを割り当てない。同じ設計項目を参照・再掲する場合は同じIDを使い、既存の設計IDや画面・帳票・連携の識別子を保持する。
- 必要な承認者の判断や外部契約を推測で確定しない。質問には選択肢・推奨と根拠・影響・確認期限の工程を添える。要件にない動きが必要なら、設計で補わず要件定義へ戻す提案をする。
- レイアウト案・図・契約ファイルは本文から参照し、どの版かわかるようにする。OpenAPIなどを併用する場合は同じ契約を矛盾する二重の正本にしない。
- 秘密値を記載しない。工程の承認と案件の状態は `status.md` と承認のコミットで扱い、文書作成や確認観点の記載を承認・受入確認済みと扱わない。

## 新規文書のテンプレート

プレースホルダーを確認済みの内容へ置き換える。不要な種類の章は省略できるが、対象外理由は概要または確認事項に残す。種類別の詳細節は対象ごとに繰り返す。

### 文書の冒頭（設計文書がないときだけ作る）

```markdown
# <機能名>の設計

入力: [<機能名>の要件](../requirements/<機能>.md)
共通設計: [README.md](README.md)
外部設計: <この文書の「外部設計」の部。不要なら理由を1行>
```
