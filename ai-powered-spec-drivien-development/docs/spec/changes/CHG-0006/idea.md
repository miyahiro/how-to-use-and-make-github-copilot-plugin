# エージェントとスキルを導入先リポジトリの .github/ に書き出せるようにする

入力・出所: 利用者の依頼（「github copilot plugin は開発マシンに紐づく設定であり、リポジトリに対して適用することができない」「sdd のエージェントやスキルを、リポジトリに適用するテンプレートのように使用したい」「`.github/extensions/` に設定してもうまく行かない」）と、確認フォームでの回答（`status.md` の Q-001〜Q-003、壁打ちでの回答）。

## 目的と課題

- 事実（利用者の確認）: エージェントプラグインは VS Code のユーザーの設定でインストールするもので、リポジトリに入れてチームに適用できない。`.github/extensions/` に置いても読み込まれない。
- 事実: Copilot がリポジトリから読み込むのは `.github/agents/*.agent.md`・`.github/skills/<名前>/SKILL.md` などの決まった場所である。workspace に同じ名前のエージェント・スキルがあると、プラグインより優先される（導入・管理ガイド）。
- 事実: CHG-0002 では、2つの形を保つ手間を避けるため、コピーでの導入をやめてプラグインだけにした。今の要件 REQ-COM-005・AC-COM-004 は「導入先の workspace へファイルをコピーさせない」と定めている。
- 人の意向: プラグインの中身を、リポジトリに適用するテンプレートとしても使いたい。プラグインでの配布は続ける（Q-001）。
- 課題: 手でコピーすると、置き場所の違いで相対リンクが切れる。また、どの版を入れたか、導入先で何を変えたかが分からなくなり、更新が難しい。

## 対象者・利用場面

- 導入する人: 導入先リポジトリのルートで書き出しスクリプトを実行し、書き出されたファイルを確かめてコミットする。新しい版が出たら、更新を実行し、差分を確かめてコミットする。
- 開発を進める利用者（チームの全員）: プラグインをインストールせずに、リポジトリを開くだけで `sdd-orchestrator` を選んで依頼できる。
- 個人でプラグインを使う人・この仕組みを開発する人: 今までどおりプラグインを使う。

## 期待する価値

- リポジトリにコミットするだけで、チームの全員が同じ版のエージェント・スキルを使える。版はリポジトリの履歴に残る。
- 元はプラグインの1つだけなので、CHG-0002 で避けた「2つの形を手で保つ手間」は増えない。
- 検査スクリプトの場所が `.github/skills/sdd-spec-check/scripts/check.mjs` に決まるため、CI から呼びやすい。
- 確かめ方: 空のリポジトリに書き出してコミットし、プラグインを入れていない VS Code で `sdd-orchestrator` が表示され、受付と検査が動くこと。

## 採用案と理由

- 推奨案・理由: プラグインを一つの元として残し、書き出しスクリプトで導入先の `.github/` に書き出す。書き出すときにリンクを書き換え、書き出した版と各ファイルのハッシュを記録する。更新では、手で変えていないファイルだけを置き換える。
- 人の判断・出所: 採用案と上の表の判断は、すべて利用者の回答による（`status.md` の Q-001〜Q-003、壁打ちでの確認フォームの回答）。
- 不採用・保留の理由: 上の候補比較のとおり。

## 対象範囲

- 今回の対象: 書き出しスクリプト（init / update / status）、リンクの書き換え、版の記録、`package.json` の実行の入口、導入・管理ガイドとユーザーガイド、テスト、要件（REQ-COM-005 などの書き直し）と設計（DES-TOOL-001・DES-TOOL-005 など）。
- 対象外: 工程の手順・エージェントとスキルの役割の変更、プラグインのスキルからの導入（Q-003）、push・PR の自動化、導入先の `.github/copilot-instructions.md` の書き換え、テンプレートリポジトリ・submodule による配布、このリポジトリ自身への `.github/` 版の書き出し（このリポジトリはプラグインで開発を続ける）、過去の変更記録の書き換え。
- 将来の候補: remove の操作、導入先での更新を知らせる仕組み（GitHub Actions など）。

## 前提・制約

- 確認済み: スキル同士のリンク（`../sdd-<名前>/SKILL.md`）と、テンプレートからスキルへのリンクは、`skills/` と `.github/skills/` で同じ形のため、書き換えなくても使える。書き換えが要るのは、エージェント・共通ルール・ユーザーガイドの中のリンクである。
- 確認済み: 検査スクリプトは、導入先の `docs/` と `.github/` の Markdown のリンク切れをエラーにする。そのため、書き出したファイルにリンク切れがあってはならない。`<名前>.new` は `.md` で終わらないので、検査の対象にならない。
- 確認済み: 検査スクリプトは実行したフォルダーを検査するので、`.github/skills/` に置いても動く。
- 仮説・未確認: `npx github:` は、導入先のマシンが GitHub からこのリポジトリを取得できることが前提になる。`.github/agents/` のエージェントでも、`tools`・`agents`・`vscode_askQuestions` がプラグインと同じように効く（同じ形式のファイルのため、効くと見込む）。`SKILL.md.new`・`*.agent.md.new` が Copilot に読み込まれない。
- 品質面で気になること: 導入する人が、書き出し・更新の結果を Git の差分で確かめてからコミットできること。スクリプトは導入先の `.github/` の決まった場所の外にファイルを書かないこと。
