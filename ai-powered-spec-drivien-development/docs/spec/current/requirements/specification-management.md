# 仕様・設計・変更記録の要件

## 目的・対象範囲

議論の結果を、原本（全体仕様）と変更記録に分けて残し、次の工程へ引き継ぐ。要件・外部設計・内部設計の作成支援、追加・修正の影響分析、整合性の検査を含む。

出典: [docs/idea/intial-idea.md](../../../idea/intial-idea.md) 第4・5・7・10章。共通要件: [common.md](common.md)。

## 機能要件・業務ルール

| ID | 大分類 | 機能 | 要件 |
| --- | --- | --- | --- |
| REQ-SPEC-001 | CAT-AUTHOR 仕様作成 | FUN-SPEC-001 | 壁打ちで課題、利用者、価値、候補・代替案、範囲、対象外を整理できること。検討中の候補と採用した内容を区別すること。 |
| REQ-SPEC-002 | CAT-AUTHOR 仕様作成 | FUN-SPEC-002 | 要件では、利用者・目的、シナリオ、機能要件、業務ルール、非機能要件、受入条件を整理し、要件 ID と受入条件 ID を付けること。軽量の案件では、要件と設計の要点を1つの文書（要点）にまとめてよいこと。 |
| REQ-SPEC-003 | CAT-AUTHOR 仕様作成 | FUN-SPEC-002 | 要件の原本を大きな機能ごとに分け、同じ文書に機能要件・非機能要件・受入条件を書くこと。小規模なら1ファイルから始められること。共通の要件は必要な場合だけ別の文書にして参照すること。 |
| REQ-SPEC-004 | CAT-AUTHOR 仕様作成 | FUN-SPEC-003 | 外部設計は、合意が必要な UI・帳票・外部連携に限ること。操作・状態・権限・入力制約・エラーを含め、内部のクラスは含めないこと。該当しない場合は理由を1行残して省けること。 |
| REQ-SPEC-005 | CAT-AUTHOR 仕様作成 | FUN-SPEC-003 | 内部設計では、業務モデル、構成、データ、処理、エラー、認証認可、共通機能、運用、テストの方針、技術的な判断を、変更の規模に応じて必要なものだけ整理できること。 |
| REQ-SPEC-006 | CAT-AUTHOR 仕様作成 | FUN-SPEC-003 | 新規開発では、DDD の用語・集約・不変条件と、プレゼンテーション・コントローラー・アプリケーション・ドメイン・インフラストラクチャの5層の責務と依存を標準として検討すること。ドメインを DB や Web フレームワークに依存させないこと。既存システムでは既存の構成を尊重し、適用する範囲と例外を人と合意すること。小さな修正に全面的な作り直しを求めないこと。 |
| REQ-SPEC-007 | CAT-AUTHOR 仕様作成 | FUN-SPEC-004 | 後から変えにくい技術的な判断を、設計判断記録（ADR）として残せること。起票は推奨で必須ではない。設計の承認で採用とし、採用後は書き換えずに新しい ADR で置き換えること。 |
| REQ-SPEC-008 | CAT-CANON 原本管理 | FUN-SPEC-005 | 原本を `docs/spec/current/`、変更記録を `docs/spec/changes/<変更ID>/` に置くこと。原本は変更ブランチで直接更新し、変更の内容は Git の差分で追えること。変更記録には、状態ファイル、タスク一覧、必要に応じてアイデア・要点・メモ・ADR だけを置き、原本の写しや差分の複製を作らないこと。完了した変更記録を、後の変更に合わせて書き換えないこと。 |
| REQ-SPEC-009 | CAT-CANON 原本管理 | FUN-SPEC-006 | 追加・修正では、既存の原本とコードへの影響（互換性、移行、回帰、承認し直す工程）を示すこと。原本を変えない修正では、理由を状態ファイルに残すこと。 |
| REQ-SPEC-010 | CAT-CANON 原本管理 | FUN-SPEC-007 | 原本と変更記録の形式上の不備（ID の重複、受入条件のない要件、リンク切れ、状態ファイル・タスク一覧の書式の誤り）を検査スクリプトで検出できること。意味の矛盾や不足はレビューで確認すること。 |

### 提供する機能

| ID | 機能 | 入力・前提 | 結果 | 停止・対象外 | 対応 REQ | 大分類 |
| --- | --- | --- | --- | --- | --- | --- |
| FUN-SPEC-001 | 壁打ち | 目的・制約・仮説。前工程の承認は不要 | 課題・利用者・価値・候補比較・採否・範囲・対象外、質問 | 検討中の案を採用案と混ぜない | REQ-SPEC-001 | CAT-AUTHOR 仕様作成 |
| FUN-SPEC-002 | 要件定義・要点 | 壁打ちの結果（軽量では依頼の内容）、既存の原本 | 機能ごとの要件・非機能要件・受入条件と ID。軽量では要点の文書 | 必要な業務判断が未確定なら止める | REQ-SPEC-002、REQ-SPEC-003、REQ-COM-004 | CAT-AUTHOR 仕様作成 |
| FUN-SPEC-003 | 外部設計・内部設計 | 承認済みの要件 | 外部の動作と例外（または省略の理由）、内部の構成・データ・処理・テスト方針 | 必須の判断や既存構成への例外が未確定なら止める | REQ-SPEC-004、REQ-SPEC-005、REQ-SPEC-006 | CAT-AUTHOR 仕様作成 |
| FUN-SPEC-004 | 設計判断記録（ADR） | 後から変えにくい判断 | ADR 案、設計の承認による採用、置き換え | 起票がないこと自体を不備としない | REQ-SPEC-007 | CAT-AUTHOR 仕様作成 |
| FUN-SPEC-005 | 原本と変更記録の管理 | 変更 ID、ブランチ | 原本の直接更新、変更記録の配置 | 原本の写しを作らない | REQ-SPEC-008 | CAT-CANON 原本管理 |
| FUN-SPEC-006 | 変更影響分析 | 既存の原本・コード・変更案 | 互換性・移行・回帰・承認し直す工程 | 読み取りだけ | REQ-SPEC-009 | CAT-CANON 原本管理 |
| FUN-SPEC-007 | 整合性の検査とレビュー | 原本・変更記録 | 検査スクリプトの結果、レビューの指摘 | レビューは読み取りだけ | REQ-SPEC-010 | CAT-CANON 原本管理 |

## 非機能要件

| ID | 要件 |
| --- | --- |
| NFR-SPEC-001 | 原本と変更記録を Git で管理し、マージ後も参照できること。変更記録を読まなくても、原本だけで全体の最新の仕様がわかること。 |
| NFR-SPEC-002 | 規模に応じて必要な文書だけを作ること。空の帳票・連携の文書や、すべての章の記入を求めないこと。 |

## 受入条件

| ID | 対象 | 条件・期待結果 |
| --- | --- | --- |
| AC-SPEC-001 | REQ-SPEC-001、REQ-SPEC-002 | 壁打ちから目的・範囲・採否の理由を追え、要件に正常・権限不足・入力不備・外部障害のうち該当する条件と受入条件がある。軽量の案件では要点の文書1つで要件と設計の要点を確認できる。 |
| AC-SPEC-002 | REQ-SPEC-003、NFR-SPEC-002 | 2つの大きな機能では文書が分かれ、各文書に非機能要件と受入条件がある。小規模な案件は1ファイルで始められる。 |
| AC-SPEC-003 | REQ-SPEC-004 | UI だけの案件で帳票・連携の文書を作らず、省略の理由が1行残る。UI の権限・入力・エラーの動作を確認できる。 |
| AC-SPEC-004 | REQ-SPEC-005、REQ-SPEC-006 | 新規案件の内部設計で集約・不変条件・5層の責務と依存の向きを確認できる。既存の5層でない構成への小さな修正では、全面的な作り直しをタスクに入れず、適用範囲と例外の合意が残る。 |
| AC-SPEC-005 | REQ-SPEC-007 | ADR 案を含む設計を承認すると、その ADR が採用として扱われる。ADR がない案件でも設計を承認できる。採用後の ADR を変えたいときは新しい ADR を作り、元の本文は変わらない。 |
| AC-SPEC-006 | REQ-SPEC-008、NFR-SPEC-001 | 変更ブランチで原本を直接更新し、`git diff` で変更内容を確認できる。変更記録には状態ファイルとタスク一覧などだけがあり、原本の写しがない。 |
| AC-SPEC-007 | REQ-SPEC-009 | 既存の機能の改善を依頼すると、影響する原本・コード・回帰テスト・承認し直す工程が示される。仕様を変えない修正では、理由が状態ファイルに残る。 |
| AC-SPEC-008 | REQ-SPEC-010 | 重複した要件 ID、受入条件のない要件、存在しないファイルへのリンク、状態ファイルの誤った値があると、検査スクリプトがその箇所を示して失敗する。 |
