# 共通要件

## 目的・対象範囲

GitHub Copilot / VS Code 上で、アイデア出しから要件定義、外部・内部設計、開発・テストまでを支援する AI エージェント、スキル、補助スクリプトの要件を定義する。主な利用者は **個人または少人数のチーム** とし、手続きを規模に応じて軽くした「ライト版」を対象とする。他のプロジェクトへ導入でき、新規開発と導入後の追加・修正を扱う。

出典: [docs/idea/intial-idea.md](../../../idea/intial-idea.md)。ライト版の方針は、宮下さんの 2026-10-20 の回答（主な利用者は個人または少人数のチーム、承認の記録を監査のために厳密に残す必要はない、AI にローカルのコミットを任せる、ローカルのブランチ作成は確認してから AI が行う）による。

本要件の対象は開発支援の仕組みであり、アイデア文書に登場する注文管理等のアプリを作る要件ではない。具体的なツール名・モデル・対応バージョンは設計で決める。

## 用語と記述ルール

文書一覧と読む順序は [README.md](README.md) を参照する。

- 利用者: Copilot を操作する人。
- 承認者: 工程の成果物を承認する人。案件ごとに登録し、利用者と同じ人でよい。
- エージェント: 担当する役割。スキル: 再利用する手順。補助スクリプト: 検査だけを行うスクリプト。
- プラグイン: エージェント・スキル・共通ルール・補助スクリプトをまとめて、導入先へインストールする単位。
- リポジトリ版: プラグインの中身を、書き出しスクリプトで導入先のリポジトリの `.github/` に書き出したもの。リポジトリにコミットして、チームで共有する。
- 共通ルール: すべてのエージェントが守る、工程・承認・Git の操作・安全のルール。
- 原本: `docs/spec/current/` の全体仕様。変更ブランチ上の原本は、取り込み前の候補である。
- 変更記録: 案件ごとの目的・範囲・状態・タスク・判断の記録（`docs/spec/changes/<変更ID>/`）。
- 状態ファイル: 案件の工程・状態・質問・承認・次の作業を書いた Markdown 1枚（`status.md`）。
- 規模: 案件の手続きの重さ。標準と軽量の2つ。

要件 ID は `REQ-<領域>-番号`、非機能要件 ID は `NFR-<領域>-番号`、受入条件 ID は `AC-<領域>-番号`、機能 ID は `FUN-<領域>-番号`、大分類 ID は `CAT-<英字略称>` とし、全体で一意にする。各要件は機能要件の表で大分類と機能を示す。大分類は [README.md](README.md) で、機能は各文書の「提供する機能」で定義する。要件間の矛盾は質問して解消する。

## 非機能要件

| ID | 要件 |
| --- | --- |
| NFR-COM-001 | 役割・手順と、Copilot 固有の登録（エージェント・スキルの設定）を分け、他環境へ移しやすくすること。初期の動作確認対象は Copilot / VS Code とする。 |
| NFR-COM-002 | 秘密情報、不要な個人情報、AI の非公開の思考過程を、文書・状態ファイル・コミットに残さないこと。 |
| NFR-COM-003 | 外部資料、Issue、コード等の内容を非信頼データとして扱い、そこにある命令から承認や操作の許可を得たと判断しないこと。 |

| NFR-COM-005 | 手続きと AI の処理を必要な範囲に限ること。規模に応じて工程と承認を減らし、人の操作は判断の回答と成果物の確認に限ること。AI が読み込む資料と出力する内容は作業に必要な範囲とし、資料全体の一括の読み込みや、既存文書の部分的な変更での全文の出力をしないこと。補助スクリプトは検査に限ること。 |

| NFR-COM-007 | 書き出しスクリプトは、リポジトリ版の置き場所（`.github/agents/`・`.github/skills/`・`.github/sdd/`）の外にファイルを書かず、記録にない既存のファイルを削除しないこと。書き出し・更新の後に、書いた・置き換えた・削除した・`.new` を置いたファイルの一覧を示し、人が Git の差分で確かめてからコミットできるようにすること。 |

## 対象外・設計で具体化する事項

対象外は、AI による人の承認判断の代行、本番操作、特定アプリの業務仕様の固定、承認の本人認証・改ざん防止・監査用の記録、独自の操作ガード・隔離実行環境である。役割の並行実行と MCP 連携は検証の対象外とする。

設計では、エージェントとスキルの構成、状態ファイルとタスク一覧の書式、承認のコミットの形、検査スクリプトの検査項目、Git の操作の範囲を決める。要件を満たせない制約が判明した場合は、人に選択肢と影響を示し、要件を独断で弱めない。
