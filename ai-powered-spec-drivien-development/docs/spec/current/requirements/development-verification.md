# 開発・テスト・検証の要件

## 目的・対象範囲

承認済みの要件・設計をタスクに分け、テスト先行の実装と独立レビューで確かめる。確認した内容と結果を残し、追加・修正と実装中の仕様変更にも対応する。

出典: [docs/idea/intial-idea.md](../../../idea/intial-idea.md) 第2・3・7・10章。共通要件: [common.md](common.md)。

## 機能要件・業務ルール

| ID | 大分類 | 機能 | 要件 |
| --- | --- | --- | --- |
| REQ-DEV-001 | CAT-DEV 開発検証 | FUN-DEV-001 | 承認済みの設計（軽量では要点）から、依存順のタスクを作ること。各タスクに、対応する要件・受入条件の ID、編集する範囲、確認の方法、完了の条件を示すこと。新しい要件をタスクの判断だけで追加しないこと。 |
| REQ-DEV-002 | CAT-DEV 開発検証 | FUN-DEV-002 | 振る舞いを追加・変更するタスクは、期待する動きのテストを先に書き、意図した理由で失敗すること（Red）、最小の実装で成功すること（Green）、振る舞いを保った整理と再実行（Refactor）を行うこと。構文や環境のエラーを Red と扱わないこと。振る舞いを伴わない文書・設定のタスクは、それに合った確認方法を使うこと。 |
| REQ-DEV-003 | CAT-DEV 開発検証 | FUN-DEV-002 | 単体・統合・契約・E2E・非機能のテストを、影響に応じて選ぶこと。画面の目視確認や手動の確認は、手順と結果を残すこと。 |
| REQ-DEV-004 | CAT-DEV 開発検証 | FUN-DEV-002 | バグ修正では、現象を再現するテストを修正の前に書くこと。追加・修正では、影響する既存の動きを回帰テストで確かめること。 |
| REQ-DEV-005 | CAT-DEV 開発検証 | FUN-DEV-003 | 確認した内容をタスク一覧に残すこと。自動のテストは実行したコマンドと結果の要点を、手動の確認は手順と観測した結果を書くこと。未実施・失敗・実行できなかったことを成功と書かないこと。 |
| REQ-DEV-006 | CAT-DEV 開発検証 | FUN-DEV-003 | 実装後に、コード・テストと受入条件を照合する独立レビューを行うこと（REQ-WF-011）。レビューの指摘への対応は、タスクとして扱うこと。 |
| REQ-DEV-007 | CAT-DEV 開発検証 | FUN-DEV-001 | 実装中に仕様の変更が必要になったら、影響する作業を止め、要件・設計（軽量では要点）へ戻して承認し直すこと。作業中のコードを捨てずに残すこと。 |
| REQ-DEV-008 | CAT-DEV 開発検証 | FUN-DEV-003 | すべてのタスクの確認と独立レビューが済んだら、結果をまとめて完了の承認を求めること。完了の承認を push・PR・マージ・本番反映の許可と扱わないこと。 |

### 提供する機能

| ID | 機能 | 入力・前提 | 結果 | 停止・対象外 | 対応 REQ | 大分類 |
| --- | --- | --- | --- | --- | --- | --- |
| FUN-DEV-001 | タスク分解と仕様変更への対応 | 承認済みの設計または要点 | 依存順のタスク一覧、仕様変更時の差し戻し | 要件・設計の不足や新しい要件が必要なら前の工程へ戻す | REQ-DEV-001、REQ-DEV-007 | CAT-DEV 開発検証 |
| FUN-DEV-002 | テスト先行の実装 | タスク、承認済みの範囲 | Red・Green・Refactor、再現テスト、回帰テスト | 意図しない失敗、環境の不足、範囲外の変更で止める | REQ-DEV-002、REQ-DEV-003、REQ-DEV-004 | CAT-DEV 開発検証 |
| FUN-DEV-003 | 確認の記録、独立レビュー、完了 | 実装、テスト、受入条件 | タスク一覧への確認結果、レビューの指摘、完了の承認依頼 | 確認が済んでいなければ完了を求めない | REQ-DEV-005、REQ-DEV-006、REQ-DEV-008 | CAT-DEV 開発検証 |

## 非機能要件

| ID | 要件 |
| --- | --- |
| NFR-DEV-001 | コードや仕様を変えた後に、変える前のテスト結果を今の結果として使わないこと。確認の結果には、そのときのコミットを添えること。 |
| NFR-DEV-002 | 実装した担当の自己評価だけで独立レビューを済ませないこと。指摘を消すために受入条件やテストを勝手に弱めないこと。 |

## 受入条件

| ID | 対象 | 条件・期待結果 |
| --- | --- | --- |
| AC-DEV-001 | REQ-DEV-001 | 承認済みの設計からタスク一覧ができ、各タスクに要件・受入条件の ID、範囲、確認方法、完了条件がある。設計に対応しないタスクは作られない。 |
| AC-DEV-002 | REQ-DEV-002 | 振る舞いを変えるタスクで、意図した失敗、最小の実装後の成功、整理後の成功が確認できる。環境のエラーだけでは Red にならない。文書のタスクにはレビューなどの確認方法が割り当てられる。 |
| AC-DEV-003 | REQ-DEV-003、REQ-DEV-005 | 自動のテストはコマンドと結果、手動の確認は手順と結果がタスク一覧に残る。実行できなかった確認は「未実施」と書かれ、完了の承認は求められない。 |
| AC-DEV-004 | REQ-DEV-004 | バグを再現するテストが修正の前に失敗し、修正の後に成功する。関連する回帰テストの結果が残る。 |
| AC-DEV-005 | REQ-DEV-006、NFR-DEV-002 | 要件に対応しないコードやテストがレビューで指摘され、対応がタスクに追加される。レビューの依頼だけではコードが変わらない。 |
| AC-DEV-006 | REQ-DEV-007 | 実装中に仕様の変更が必要になると作業が止まり、要件・設計へ戻って承認し直してから再開する。作業中のコードは残る。 |
| AC-DEV-007 | REQ-DEV-008、NFR-DEV-001 | すべてのタスクの確認とレビューが済むと完了の承認を求め、承認後も push・マージは行わない。コードを変えた後に古い結果のまま完了を求めない。 |
