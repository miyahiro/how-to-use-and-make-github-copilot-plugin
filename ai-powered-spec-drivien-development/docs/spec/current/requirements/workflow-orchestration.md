# ワークフロー・エージェント連携の要件

## 目的・対象範囲

対話の窓口を一本化し、規模に応じた工程で、人の承認を得ながら次の工程へ進める。承認はローカルのコミットとして残し、状態は案件ごとの状態ファイルで管理する。状況確認、中断・再開、スキルの直接指定も対象とする。

出典: [docs/idea/intial-idea.md](../../../idea/intial-idea.md) 第3・6・7・9章。共通要件: [common.md](common.md)。

## 機能要件・業務ルール

| ID | 大分類 | 機能 | 要件 |
| --- | --- | --- | --- |
| REQ-WF-001 | CAT-FLOW 工程進行 | FUN-WF-001 | 受付で、変更の種別（新規・改善・修正）、目的、対象と対象外、規模（標準・軽量）、承認者を確認し、既存と重ならない変更 ID を付けること。規模は AI が推奨を示し、人が決めること。受付の内容で状態ファイルを作ること。承認者の名前を推測で登録しないこと。 |
| REQ-WF-002 | CAT-FLOW 工程進行 | FUN-WF-001 | 1つの変更を1つのローカルブランチで扱うこと。受付で AI がブランチ名を示し、人の確認を得てから作成・切り替えること。Git が未初期化の場合や、未コミットの変更があって切り替えられない場合は、状況と選択肢を示して人に判断を求めること。 |
| REQ-WF-003 | CAT-FLOW 工程進行 | FUN-WF-002 | 規模に応じて工程を選ぶこと。標準は「壁打ち → 要件 → 設計 → 実装 → 完了」とし、要件・設計・完了で承認を求めること。軽量は「要点 → 実装 → 完了」とし、要点（要件と設計の要点をまとめたもの）と完了で承認を求めること。承認のない工程の成果物を前提に、後の工程の正式な作業を始めないこと（後の工程の案の作成やレビューは可）。工程の区切り（受付の後、壁打ちの合意の後、工程の承認の後）では次の作業を示して止まり、人の依頼を受けてから次の工程を始めること。途中で規模を変える場合や前の工程へ戻す場合は、人の確認を得ること。 |
| REQ-WF-004 | CAT-FLOW 工程進行 | FUN-WF-003 | 承認を求めるときは、工程、対象のファイル、変更の要点を示すこと。人の明確な肯定（確認フォームの「承認する」、または「承認します」などの明確な回答）だけを承認とし、「続けて」、条件付き、疑問、保留の回答は聞き直すこと。登録された承認者以外の回答では承認しないこと。 |
| REQ-WF-005 | CAT-FLOW 工程進行 | FUN-WF-003 | 承認を得たら、AI がその工程の成果物と状態ファイルを、承認者・日時・工程がわかる形でローカルにコミットすること。承認の後に対象の成果物が変わった場合は、その工程を承認し直すこと。過去の承認はコミットの履歴として残すこと。 |
| REQ-WF-006 | CAT-FLOW 工程進行 | FUN-WF-003 | 工程の承認は、次の工程の範囲での文書・コードの編集、ローカルでのテストの実行、作業の区切りのコミットの許可を兼ねること。範囲外の変更、ファイルの削除、新しい依存の追加は、個別に確認すること。push・PR・マージ・本番反映は AI が行わず、人に案内すること。 |
| REQ-WF-007 | CAT-FLOW 工程進行 | FUN-WF-005 | 案件ごとに状態ファイルを1つ持ち、工程・状態・質問・承認・次の作業を、人が読み書きできる Markdown で保つこと。AI は作業の区切りごとに更新すること。人が編集してもよいこと。会話をまたいでも、状態ファイルと Git の履歴から再開できること。 |
| REQ-WF-008 | CAT-FLOW 工程進行 | FUN-WF-005 | 状況確認は読み取りだけとし、状態ファイルと検査スクリプトの要約だけを使って、工程・状態・期限の来た質問・承認待ち・承認後に変わった成果物・タスクの状況・次の作業を答えること。案件の成果物を個別に読み込まないこと。 |
| REQ-WF-009 | CAT-FLOW 工程進行 | FUN-WF-005 | 「止めて」と依頼されたら新しい作業を止め、状態ファイルに中断と次の作業を書くこと。再開では、ブランチ、承認後の変更、期限の来た質問を確かめ、不一致があれば解消してから続けること。 |
| REQ-WF-010 | CAT-FLOW 工程進行 | FUN-WF-006 | 窓口が人との対話を受け持ち、必要な担当にだけ作業を任せること。委任ではパス・範囲・要点だけを渡し、文書の本文を渡さないこと。返却では変更したファイルと要点だけを受け取ること。窓口は文書を読み直さず、Git の差分の一覧で返却を確かめること。作業で分かった知識（調べて分かった事実、作業上の前提、試してうまくいかなかったこと、テストや起動の方法）は案件の作業メモに残し、委任ではそのパスも渡すこと。作業メモは承認の対象とせず、決定事項・原本の写し・秘密の値を書かないこと。 |
| REQ-WF-011 | CAT-FLOW 工程進行 | FUN-WF-006 | 実装後のレビューは、実装とは別のレビュー担当（読み取り専用）または別の人が行うこと。役割名を変えただけの自己確認を独立レビューと扱わないこと。サブエージェントを使えない場合はそのことを示し、人の確認で代えられること。 |
| REQ-WF-012 | CAT-FLOW 工程進行 | FUN-WF-006 | 利用者がスキルを直接指定した場合も、その工程の前提を確認すること。壁打ち・質問整理・深掘り・状況確認・レビューは、承認なしで使えること。レビューの依頼だけではファイルを変更しないこと。 |
| REQ-WF-013 | CAT-FLOW 工程進行 | FUN-WF-004 | 承認の前に、任意で成果物を深掘りできること。AI が判断の分かれ道を前提の順に1問ずつ、推奨の答えと理由を付けて聞き、コードや原本で分かることは人に聞かずに調べること。答えは質問と同じく状態ファイルと成果物へ反映し、人が止めたらすぐに止めること。深掘りを承認の条件にしないこと。 |

## 非機能要件

| ID | 要件 |
| --- | --- |
| NFR-WF-001 | 会話を読み返さなくても、状態ファイルを開けば案件の状況と次の作業がわかること。 |
| NFR-WF-002 | 1つの案件で人に求める承認は、標準で3回（要件・設計・完了）、軽量で2回（要点・完了）を上限とすること。利用者と承認者が同じ人でも、同じ工程で承認を二重に求めないこと。 |

## 受入条件

| ID | 対象 | 条件・期待結果 |
| --- | --- | --- |
| AC-WF-001 | REQ-WF-001、REQ-WF-002 | 受付で種別・目的・範囲・規模・承認者を確認し、変更 ID と状態ファイルができる。ブランチ名を示し、人が確認すると作成・切り替えされる。人が断るとブランチは作られない。 |
| AC-WF-002 | REQ-WF-003、NFR-WF-002 | 軽量の案件は「要点 → 実装 → 完了」で進み、承認は2回で済む。標準の案件で要件の承認がないまま設計の正式な作業を頼むと止まり、設計の案の作成やレビューは使える。受付・壁打ちの合意・承認の後は次の作業が示されて止まり、依頼すると次の工程が始まる。 |
| AC-WF-003 | REQ-WF-004 | 「続けて」「良さそう」「承認します、ただし〜」では承認せず、聞き直す。承認者以外の回答では承認しない。確認フォームの「承認する」または「承認します」で承認として扱う。 |
| AC-WF-004 | REQ-WF-005 | 承認すると、成果物と状態ファイルがローカルにコミットされ、コミットから工程・承認者・日時がわかる。承認後に成果物を編集すると、状況確認でその工程が再承認の対象として示される。 |
| AC-WF-005 | REQ-WF-006 | 要件の承認後、設計の文書の編集とローカルのコミットは改めて確認せずに行われる。範囲外のファイルの削除や新しい依存の追加は確認される。push を頼んでも実行せず、手順を案内する。 |
| AC-WF-006 | REQ-WF-007、NFR-WF-001 | 状態ファイルを開くと、工程・状態・未解決の質問・承認・次の作業がわかる。人が状態ファイルを編集しても、次の作業でその内容が使われる。別の会話から変更 ID を伝えると再開できる。 |
| AC-WF-007 | REQ-WF-008 | 「状況を教えて」と頼むと、状態ファイルと検査スクリプトの要約だけで答え、成果物を個別に読まない。状況確認の前後でファイルは変わらない。 |
| AC-WF-008 | REQ-WF-009 | 「止めて」で作業が止まり、状態ファイルに中断と次の作業が書かれる。別のブランチにいる状態で再開を頼むと、不一致を示して止まる。 |
| AC-WF-009 | REQ-WF-010 | 設計を委任すると、担当にはパスと範囲だけが渡り、返却には変更したファイルと要点だけが含まれる。窓口は差分の一覧で照合し、文書を読み直さない。返却と実際の変更が食い違うと採用しない。委任には作業メモのパスが含まれ、担当が調べて分かったことはメモに追記され、返却の要点にそのことが示される。 |
| AC-WF-010 | REQ-WF-011 | サブエージェントを使えない環境で役割を切り替えただけでは、独立レビュー未実施と表示する。別の人が確認した結果を伝えると、独立レビュー済みとして記録できる。 |
| AC-WF-011 | REQ-WF-012 | 承認前の成果物でも、壁打ち・質問整理・深掘り・状況確認・レビューを直接指定して使える。レビューだけの依頼ではファイルが変わらない。 |
| AC-WF-012 | REQ-WF-013 | 承認を求める前に深掘りが一度だけ提案され、断ると深掘りなしで承認に進める。深掘りでは1問ずつ推奨付きで聞かれ、原本やコードで分かることは聞かれない。答えが状態ファイルの質問の表と成果物に残り、「ここまで」と答えると止まる。 |
