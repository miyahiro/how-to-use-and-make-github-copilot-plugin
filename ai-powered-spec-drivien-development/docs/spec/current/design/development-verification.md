# タスク・TDD・レビュー・検証設計

入力: [開発・検証要件](../requirements/development-verification.md)。

## DES-DEV-001 タスク分解

- 実装担当が、承認済みの設計（軽量では要点）から `tasks.md`（DES-SPEC-004）を作る。各タスクに要件・受入条件の ID、設計 ID、確認方法、編集する範囲と完了の条件（内容の列に書く）を持たせ、内部設計の依存の向きと移行の順に従って並べる。確認方法は内部設計のテスト設計と外部設計の確認観点から決める。
- 振る舞いのタスクの確認方法は TDD、文書・設定のタスクはレビューや設定の検証とする。
- 設計にないことが必要になったら、タスクを増やさず窓口へ返す。窓口は前の工程へ戻すかを人に聞く。

## DES-DEV-002 テスト先行の実装

- Red: 期待する動きのテストを書き、意図した理由で失敗することを確かめる。構文・依存・環境のエラーは直してからやり直す。
- Green: 最小の実装で成功させる。
- Refactor: 振る舞いを保って整理し、同じテストと関連する回帰テストを再実行する。
- バグ修正は、現象を再現するテストから始める。
- テストの種類（単体・統合・契約・E2E・非機能）は影響に応じて選ぶ。手動の確認が必要なら、手順と期待する結果を人に示し、観測した結果を答えてもらう。
- 確認の結果は `tasks.md` の「結果」に書く（コマンドと結果の要点とコミット、または手順と観測）。コードを変えた後は、前の結果を使わずに再実行する。

## DES-DEV-003 レビューと完了

- 実装後、窓口が `sdd-reviewer` に、対象のパスと受入条件の ID を渡してレビューを依頼する。レビュー担当は読み取りだけで、指摘を重大度順に返す。
- サブエージェントが使えない場合は「独立レビュー未実施」と示し、別の人の確認結果を `status.md` の「次の作業」かメモに書いて代える。
- 指摘への対応は `tasks.md` にタスクとして追加する。
- すべてのタスクが `done` か `dropped` で、確認とレビューが済んだら、窓口が完了の承認（`completion`）を求める。承認のコミット後、push・PR・マージの手順を案内する。

## DES-DEV-004 受入確認計画

以下は実装後の確認計画である。検査スクリプトとプラグインの構成はテスト（リポジトリのルートで `npm test`）で確認し、対話の動作はローカルに登録したプラグインを使った Copilot Local での試行とレビューで確認する。役割の並行実行と MCP 連携は確認しない。

| 受入条件 | 確認方法・期待する観測 |
| --- | --- |
| AC-COM-001 | Copilot Chat で開始の依頼をし、受付が始まる |
| AC-COM-002 | 性能が未定のまま壁打ちを続け、要件の承認の前に質問される |
| AC-COM-003 | 「続けて」で承認されず、「承認します」で承認される |
| AC-COM-004 | 空のプロジェクトで、マーケットプレイスを登録してプラグインをインストールし、workspace にファイルが増えず、依存のインストールなしに検査と開始の依頼が動く。版を上げたプラグインの更新が反映される |
| AC-COM-005 | ダミーの秘密と命令入りの資料で、秘密が記録されず命令が実行されない |
| AC-COM-006 | 無関係な変更がある状態で承認のコミットをし、その変更が含まれない |
| AC-COM-007 | 軽量の案件の承認が2回で済む。指示に資料全体を読む手順がないことをレビューする |
| AC-COM-008 | push を頼んで実行されず、手順が案内される |
| AC-COM-009 | 4つのエージェントの本文の冒頭に共通ルールへのリンクがあり、共通ルールの本文が1か所だけにあること（テスト）。各エージェントで作業を始めると共通ルールが読まれる（試行） |
| AC-COM-010 | `chat.pluginLocations` に登録して、エージェントとスキルが表示される（試行）。構成のテストが欠け・名前の不一致・リンク切れを見つける（テスト） |
| AC-WF-001 | 受付で状態ファイルができ、確認後にブランチが作られる。断るとブランチがない |
| AC-WF-002 | 軽量の流れ、標準で要件の承認前に設計を頼んで止まる、承認の後は次の作業を示して止まり依頼で次の工程が始まる |
| AC-WF-003 | 曖昧な回答と承認者以外の回答で承認されない |
| AC-WF-004 | 承認のコミットができ、承認後の編集が検査スクリプトで再承認として示される（テスト） |
| AC-WF-005 | 承認後の範囲内の編集とコミットに確認が入らず、削除と依存の追加に確認が入る |
| AC-WF-006 | 状態ファイルの内容と、人の編集の反映、別の会話からの再開 |
| AC-WF-007 | 状況確認が状態ファイルと検査スクリプトの要約だけで行われ、ファイルが変わらない |
| AC-WF-008 | 中断の記録と、別ブランチでの再開の停止 |
| AC-WF-009 | 委任と返却がパスと要点で行われ、`git diff --stat` で照合される、作業メモのパスが委任に含まれ、追記が返却に示される |
| AC-WF-010 | 役割の切り替えだけでは独立レビュー未実施と示される |
| AC-WF-011 | 承認前の成果物のレビューでファイルが変わらない |
| AC-WF-012 | 承認前の深掘りの提案と辞退、1問ずつの質問、記録、止める指示 |
| AC-SPEC-001 | 壁打ちから要件への追跡と、軽量の要点の文書 |
| AC-SPEC-002 | 2つの機能の文書の分割と、小規模の1ファイル |
| AC-SPEC-003 | UI だけの案件で不要な文書が作られない |
| AC-SPEC-004 | 新規の内部設計の5層と、既存構成での例外の合意 |
| AC-SPEC-005 | ADR 案の承認後の扱いと、置き換え |
| AC-SPEC-006 | 原本の直接更新と、変更記録に写しがないこと |
| AC-SPEC-007 | 影響分析の内容と、仕様を変えない修正の理由の記録 |
| AC-SPEC-008 | 重複 ID・受入条件のない要件・リンク切れ・状態ファイルの誤りを検査スクリプトが検出する（テスト） |
| AC-DEV-001 | タスク一覧の各列と、設計に対応しないタスクがないこと |
| AC-DEV-002 | 1つの振る舞いのタスクで Red・Green・Refactor を確かめる |

| AC-DEV-004 | バグの再現テストの修正前後 |
| AC-DEV-005 | レビューの指摘がタスクに追加され、レビューだけではコードが変わらない |
| AC-DEV-006 | 実装中の仕様変更で止まり、承認し直してから再開する |
| AC-DEV-007 | 完了の承認後も push されない |
| AC-TOOL-001 | MCP なしで全工程を進める |
| AC-TOOL-002 | 承認のコミットの内容と、push・リベースの不実行 |
| AC-TOOL-003 | テストの実行前にコマンドが示される |
| AC-TOOL-004 | 1か所の修正が差分の編集で行われる |

| AC-TOOL-006 | ダミーの秘密が出力で伏せられる（テスト） |
