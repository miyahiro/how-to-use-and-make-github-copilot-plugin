# 記事公開の設計

入力: [記事公開の要件](../requirements/article-publication.md)

## 外部設計

### 1. 設計対象・概要

- 利用編・作成編を別々の Qiita 向け Markdown 原稿として完成する。読者・目的は各記事の要件に従い、記事を統合しない。
- 関連要件: REQ-PUB-001〜003、NFR-PUB-001。
- 関連受入条件: AC-PUB-001〜003。
- Qiita への実投稿・アカウント操作は本設計の対象外とし、原稿完成の受入条件にしない。投稿は利用者が行う。
- 社内 marketplace の配布元は利用対象者だけにアクセスを許可した GitHub private repository とする一方、記事は Qiita 向けの公開原稿である。公開原稿に認証情報・秘密の値や、利用者の認証を代替する情報を含めず、社内限定の配布手順と公開記事の参照情報を区別する。

| --- | --- | --- | --- | --- |

### 3. 外部公開前の確認

- 2本がそれぞれ Qiita に移せる Markdown になっており、題名・見出し・本文・リンクの参照先があることを確認する。
- 公開先への実投稿は原稿作成と分離する。AI による投稿代行は行わず、投稿の有無を原稿受入の条件にしない。
- 調査・動作確認が未実施の項目は記事内で未確認とし、実施済みと誤認させない。
- 両記事に「動作確認環境」章があり、確認日・環境とバージョン・対象 Plugin の版・確認範囲が検証記録と一致することを確認する。一方の記事だけを読んでも確認済み環境と未確認事項が分かる構成にする。

| 項目 | 要件・受入条件 | 確認観点 |
| --- | --- | --- |
| 原稿確認 | REQ-PUB-001〜003 / AC-PUB-001〜003 | 記事が独立し読者と目的が異なる。各原稿の Markdown 構造と参照が確認でき、分量より理解しやすさが優先される。実投稿は合否から除外される。 |

## 内部設計

### 1. 文書作成・品質確認

- 編集方針メモ（利用編・作成編共通）: 設計書の章立て・掲載内容は実機検証の結果に応じて変更・削除する。検証で想定どおりに動作しなかった機能・手順は、原則として記事に記述しない。動作確認できた内容を中心に章を再構成し、失敗した手順を利用可能な手順として掲載しない。検証の失敗結果自体は検証記録に残す。
- 上記の見直しで承認済み要件・受入条件に定めた説明を削除する必要が生じた場合は、要件との整合を確認し、必要な要件修正・再承認を経て反映する。現時点では要件の削除や、制約・確認状況を明示する既存方針の撤回は行わない。
- 対象は記事原稿の編集とレビューであり、ソフトウェア、業務ドメイン、画面、データモデル、DDD の層は存在しない。
- 利用編・作成編それぞれの設計文書にある章構成と検証記録を参照し、公開用原稿の内容に対応させる。
- Qiita 固有の投稿操作や外部サービス連携の実行はしない。Markdown の構造、内部リンク、外部参照先、事実確認状態を原稿レビューで確かめる。
- 作成編には private marketplace の認証・アクセス権確認と取得・導入・更新の説明を反映する。公開前に、private repository の資格情報や非公開のアクセス手段を露出していないこと、および配布元のアクセス制御が導入後の複製・再配布を防ぐ保証だと誤認させないことを確認する。未検証の URL、manifest、CLI 構文や特定クライアントの非公開リポジトリ直接登録対応は、確認済みの事実として記載しない。

### 3. 変更影響

- 公開先は要件で Qiita に決まっている。記事本文の作成・投稿以外の公開システム実装はない。
- Q-3 の回答を受け、社内 marketplace は利用対象者だけにアクセスを許可した GitHub private repository で管理する。これは作成編の説明対象を定めるが、記事公開先 Qiita と社内配布元を分離し、公開原稿に機密値・認証情報を含めない確認が必要になる。private repository は取得後の複製・再配布を防止しないため、その保証を示唆しない。
