# GitHub Copilot Plugin 作成編の設計

入力: [作成編の要件](../requirements/plugin-authoring.md)

## 外部設計

### 1. 設計対象・概要

- 対象: 開発リーダーが簡単な Plugin を新規作成し、VS Code の対象環境で導入・実行を確認する記事の構成。
- 関連要件: REQ-AUTHOR-001〜007、NFR-AUTHOR-001。
- 関連受入条件: AC-AUTHOR-001〜007。
- VS Code 1.145.2 を前提とする。manifest、ディレクトリ規則、導入 UI、marketplace 定義の具体仕様は公式リファレンスで照合するまで確定済みの手順として掲載しない。
- 記事・サンプルはソフトウェア実装ではない。説明用サンプルに不要な DDD モデルや UI 設計を加えない。

### DES-AUTHOR-001: 作成編の章構成

章立て・掲載内容は実機検証の結果に応じて変更・削除する。想定どおり動作しなかった機能・手順は原則掲載しない。両記事共通の扱いと要件との整合確認は、[記事公開の設計の編集方針メモ](article-publication.md#1-文書作成品質確認)に従う。

| 区分 | 章 | 読者の流れ・記事に含める内容 | 関連要件 | 受入条件 |
| --- | --- | --- | --- | --- |

### 3. サンプルの外部動作

#### DES-AUTHOR-002: 「変更引き継ぎメモ」Plugin の題材・期待結果

- 目的: 開発者が入力した変更メモを、次の担当者に渡す短い要約へ整える、文章指示だけの小さな例とする。
- 入力: 読者が手動で与える任意の短い変更メモ。自動的にリポジトリを走査したり、ファイルを書き換えたりしない。
- 期待する回答: 「目的」「変更点」「確認事項」の3項目に分けた要約。与えられていない情報は推測せず「記載なし」とする。
- 範囲: 単一の Copilot 向け skill を含む最小の Plugin を想定する。hooks、MCP server、外部 API、生成コードは含めない。manifest と marketplace 定義の最小ファイル内容・命名・配置は公式仕様確認後に記事で確定する。
- 導入・実行操作: VS Code 1.145.2 の公式にサポートされたローカル／marketplace 導入方法を照合して採用する。CLI コマンドを含める場合はコマンド仕様を別途確認し、未確認のまま記事の再現手順にしない。

| 項目 | 要件・受入条件 | 外部から確認できる結果 |
| --- | --- | --- |
| ハンズオン例 | REQ-AUTHOR-004, 007 / AC-AUTHOR-004, 007 | 新規作成したサンプルを導入し、既知の入力メモで3項目の要約を生成する。入力にない事実は「記載なし」等となり、ファイル変更・外部通信など意図しない副作用がない。 |

## 内部設計

### 1. 対象と例の構成

- 記事内の例は学習用のファイル一式であり、アプリケーションの実装を本案件で作るものではない。
- 配置の設計案は Plugin ルート、manifest、Copilot 固有 skill の本文、および配布用 marketplace 定義。marketplace 定義とサンプル Plugin は同じ private repository で管理する。正確な相対パス、ファイル名、manifest の必須項目、marketplace の schema は公式の Agent plugin authoring reference で確認後に固定する。
- 本設計の範囲外: sdd の改変、拡張機能・MCP server・hook の実装、社内配布の実操作。

### 2. 作成手順と確認点

#### DES-AUTHOR-003: 再現可能なハンズオンの流れ

1. サンプルを導入していない新しい検証 Workspace を用意し、対象の VS Code と Copilot のバージョン、利用可能な harness、実施者を記録する。
2. 記事に示す構成を空の作業用ディレクトリへ新規作成する。各ファイルに掲載する実際の内容は公式 schema と記述形式に照合済みのものに限定する。
3. manifest と Plugin 構成を確認する。名前・説明等の識別情報、skill の名前空間・配置、marketplace 定義が公式仕様と整合することを確認する。
4. 対象環境でサポートされた導入操作を行い、Copilot 側で Plugin の skill が利用可能であることを確認する。
5. 「ログ出力を追加した。テスト未実施。」等の固定入力で実行し、目的・変更点・確認事項の3項目が返ること、未実施を完了と偽らないことを確認する。
6. 同じ入力で、サンプルがない環境との混同がないことを確かめる。導入・実行に失敗した場合は原因と環境を記録し、未成功とする。代替操作は別途実機確認する。

| 手順 | 確認対象 | 成功条件 | 未確認・失敗時の扱い |
| --- | --- | --- | --- |
| 手順検証 | ファイル構成・manifest | 公式仕様にある必須構造と各ファイルの配置に適合する。 | 仕様を確認できなければ手順に確定値として書かない。 |
| 手順検証 | 導入・発見・実行 | 記事の手順を新規環境で再現し、期待した skill を実行できる。 | エラー、未対応 harness、未実施を成功とせず、環境・結果を記録する。 |
| 手順検証 | 内容の振る舞い | 固定入力で3項目の回答が得られ、欠落情報を創作しない。 | 出力が期待と異なる場合、記事の例・期待結果を直して再検証する。 |

### 3. sdd 参考例との対応

#### DES-AUTHOR-004: sdd の構成を参照する

| 項目 | sdd の観察対象 | 作成編で示す関係 | 関連要件・受入条件 |
| --- | --- | --- | --- |
| 参考例 | Plugin 本体、ルートの `plugin.json`、`skills/`、`com.github.copilot/agents/`、marketplace の所在 | 本体の構成、Copilot 固有要素、および配布用 marketplace 定義の役割を参照例として対比する。sdd の規模・固有手順は最小サンプルの要件にしない。 | REQ-AUTHOR-003 / AC-AUTHOR-003 |

参照したリポジトリ内 sdd の構成事実は `ai-powered-spec-drivien-development/plugins/sdd/README.md` と `ai-powered-spec-drivien-development/plugins/sdd/plugin.json` にある。これらの現行ファイルを例に使う場合、記事作成時点の版・参照先を再確認する。公式仕様としての正確さは公式リファレンスで別途検証する。

### 4. 社内 marketplace の管理・利用

#### DES-AUTHOR-005: GitHub private repository を使った配布

- 管理場所: 利用対象者だけにアクセスを許可する GitHub private repository を marketplace の配布元とする。marketplace 定義とサンプル Plugin のソースを同じリポジトリ内に置き、定義からサンプルの所在を参照する構成とする。配置・manifest・marketplace 定義の具体的なパスや schema は公式仕様との照合後に記事で確定する。
- 認証・権限: 利用者は許可された GitHub アカウントで認証し、対象リポジトリへの読み取り権限があることを取得前に確認する。権限申請先・付与・見直しはリポジトリ管理者の責務とし、権限のない利用者にはリポジトリ内容を取得させない。資格情報や機密値を記事・サンプル・ログに記載しない。
- 取得・導入: 許可された利用者が認証済み環境からリポジトリを取得し、marketplace 定義、参照先、Plugin のコード・設定、更新履歴を確認する。非公開リポジトリを特定クライアントへ直接登録できるとは仮定しない。認証済みのローカル clone を経由する方法は検証候補とし、対象の VS Code 1.145.2、利用する harness／クライアントごとに、公式資料で対応方式・構文を照合し、新しい環境で取得、登録、サンプル導入、実行まで確認した手順だけを記事に載せる。
- 更新: 利用者は認証済み clone を更新して対象の変更・版を確認し、提供元・コード・設定を再レビューしたうえで、公式にサポートされた方法で marketplace と Plugin を更新する。更新前後の版・変更点・動作確認結果を記録する。取得・marketplace 登録・Plugin 更新の URL、manifest、CLI 構文は未照合のため、本設計では実行可能な確定コマンドとして示さない。
- 配布元のアクセス制御は取得前の閲覧・取得範囲を制限するものであり、許可された利用者が導入後にファイルを複製・再配布することを技術的に防ぐ保証ではない。記事ではこの限界を明記し、private repository の利用を導入先での再配布防止策として説明しない。
- 配布前に提供元、ソース内容、必要設定、版・変更履歴、更新責任者を確認する（REQ-AUTHOR-006）。配布元の管理と利用者への提供・更新責任を明確にする。

| 要件・受入条件 | 設計ID | 確認観点 |
| --- | --- | --- |
| REQ-AUTHOR-005, 006 / AC-AUTHOR-005, 006 | DES-AUTHOR-005 | 対象利用者だけが取得できる権限設定、認証済み利用者の取得・導入・更新手順、提供元・コード・設定・版・更新責任の確認をレビューする。private repository が導入後の再配布まで防ぐと誤認させない。手順は対象環境で検証済みの範囲と未確認事項を分ける。 |

#### 手順確定前の検証事項

Q-3 は利用者回答に基づき GitHub private repository 上の marketplace 管理として設計に反映した。これは配布方式の選択であり、実機検証の完了や設計承認を意味しない。記事の具体的な手順を確定する前に、GitHub 認証済みの新しい環境でリポジトリへのアクセス権、取得、ローカル clone からの marketplace 登録、サンプル Plugin の導入・実行、更新を確認する。特定クライアントの非公開リポジトリ直接登録の対応は仮定せず、公式資料と検証結果で確認する。
