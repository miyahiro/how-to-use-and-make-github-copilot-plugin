# 記事公開の要件

入力: [CHG-0001 idea.md](../../changes/CHG-0001/idea.md)

## 目的

利用編・作成編を別々の記事として Qiita で公開できる状態にする。

## 利用者と利用場面

| 利用者・役割 | 契機・事前状態 | 代表的なシナリオ |
| --- | --- | --- |
| 記事の作成者 | 利用編・作成編の原稿がそろっている | 2本をそれぞれ独立した記事として公開する |
| 各記事の読者 | Qiita で関心のあるテーマを見つける | 自分に合う記事を選び、内容を読み進める |

## 対象範囲

- 対象内: 利用編・作成編を独立した記事として用意し、Qiita を公開先とする。
- 対象外: 実際の Qiita アカウント操作や投稿の代行。
- 前提・外部との境界: 原稿を Qiita に投稿する作業は利用者が行う。記事の内容・形式を公開先に適合させる。

## 機能要件

| ID | 要件 | 出所 |
| --- | --- | --- |
| REQ-PUB-001 | 利用編と作成編は、読者と目的の異なる2本の独立した記事として構成する。 | 利用者の回答、CHG-0001 idea.md |
| REQ-PUB-002 | 各記事は Qiita で公開することを前提とした Markdown 原稿として完成させ、記事ごとの題名と本文を備える。 | 利用者の回答 |
| REQ-PUB-003 | 各記事は約20分を読了時間の目安とし、読了時間に合わせることより読者の理解しやすさを優先する。 | 利用者の回答 |

## 業務ルール

| ルール | 関連要件 ID |
| --- | --- |
| 利用編と作成編の内容を一つの記事に統合しない。 | REQ-PUB-001 |
| 外部サービスへの投稿は記事の原稿完成とは分け、Qiita への実投稿は利用者が行う。実投稿は原稿の受入判定の必須条件に含めず、AI による投稿代行は行わない。 | REQ-PUB-002 |
| 約20分は目安であり、根拠のない厳密な文字数や読み上げ速度を受入基準として設定しない。 | REQ-PUB-003 |

## 非機能要件

| ID | 要件・適用範囲 | 測定条件・判定基準 | 出所 |
| --- | --- | --- | --- |
| NFR-PUB-001 | 2本の記事は対象読者ごとに読みやすく、Qiita に移せる Markdown とする。 | 各記事の題名・見出し・本文・リンクが確認でき、各記事の理解しやすさをレビューする。 | 利用者の回答 |

## 受入条件

| ID | 対応要件 ID | 事前状態 | 操作・事象 | 観測可能な期待結果 |
| --- | --- | --- | --- | --- |
| AC-PUB-001 | REQ-PUB-001 | 2本の記事原稿がある | 構成と読者を確認する | 利用編と作成編が別々の題名・本文を持ち、対象読者と目的が区別されている |
| AC-PUB-002 | REQ-PUB-002, NFR-PUB-001 | 2本の記事原稿がある | Qiita 向けの原稿として確認する | 各原稿に題名・見出し・本文があり、Markdown として参照先を確認できる。利用者による Qiita への実投稿の有無は合否に影響せず、AI による投稿代行は行っていない |
| AC-PUB-003 | REQ-PUB-003 | 2本の記事原稿がある | 分量と説明の明瞭さをレビューする | 各記事がおよそ20分で読める量を目指し、長さより理解しやすさを優先した構成になっている |
